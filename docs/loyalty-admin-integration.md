# SIZEY: параллельная интеграция бонусного кабинета в Hub Admin

Статус: технический план, без изменений работающих сервисов и данных.

## Неизменяемые условия

1. `https://app.sizey.ru` остаётся рабочим со всеми текущими функциями, маршрутами, сотрудниками и сессиями. Нельзя заменять его frontend, перенаправлять пользователей или отключать его.
2. `https://admmm.sizey.ru` получает аналогичные функции через **существующий** бонусный backend. Оба интерфейса используют одни и те же записи клиентов, бонусные лоты, транзакции и настройки.
3. Не создавать вторую бонусную базу, не делать прямых записей в PostgreSQL из Hub API, не переносить балансы, не изменять существующую бизнес-логику.
4. Все денежные и бонусные мутации выполняются только существующими backend-операциями с их валидацией, аудитом, авторизацией и защитой от повторного выполнения.
5. Выпуск новых функций — через отдельную ветку, тесты и canary; развертывание Hub Admin не перезапускает `sizey-prod-backend`, `app.sizey.ru` и бонусную PostgreSQL.

## Проверено по исходникам этого репозитория

- `src/admin/main.tsx`: админка React; есть «Клиенты» с внешней ссылкой на `app.sizey.ru`, но нет встроенных операций бонусной системы.
- `server/admin.mjs`: cookie `__Host-sizey_admin`, 15-минутная серверная сессия, проверка `staffAuth.me()` на каждом защищённом запросе; только `ADMIN` и активные сотрудники. В сессии хранится токен сотрудника на сервере.
- `server/staff.mjs`: известны `POST /api/auth/login` и `GET /api/auth/me` действующего backend; других контрактов здесь нет.
- `server/loyalty.mjs`: чтение клиентов, текущего баланса по действующим `bonus_lots` и 50 последних `transactions` через read-only PostgreSQL; **не** API для мутаций.
- `server/start.mjs`: Hub API подключён к отдельному read-only источнику бонусных данных.
- `integrations/bonus-cabinet/home-page.tsx`: `GET /api/clients?all=true`, `GET /api/clients/search?q=...`, экраны `/clients/new` и `/clients/:id` в существующем Next.js.
- `integrations/bonus-cabinet/customer-access-api.ts`: `POST /api/auth/refresh`; доступ к выдаче пароля через same-origin `/api/customer-access/:id`.
- `integrations/bonus-cabinet/route.ts`: проверка UUID, bearer-токена и Origin, проксирование на `/hub-api/staff/clients/:id/access|issue`; роли `ADMIN/CASHIER` проверяются Hub API.
- `deploy/hub-Caddyfile`: `/hub-api/*` идёт в `sizey-hub-api:8080`; отдельный хост админки использует `/srv/current/admin`.

**Ограничение аудита:** исходники основного Next.js кабинета и `sizey-prod-backend` не входят в данный репозиторий. Не считать приведённые выше маршруты полным API; не придумывать пути для начислений, списаний, продаж, возвратов, уровней и сотрудников.

## Целевая схема

```text
app.sizey.ru (не меняем) -----> sizey-prod-backend -----> loyalty PostgreSQL
                                     ^
                                     | внутренние API, единые правила
                                     |
admmm.sizey.ru --> sizey-hub-api (BFF) 
                    | серверная admin cookie, проверка роли на каждом запросе
                    | токен сотрудника не раскрывается браузеру
                    +--> sizey-prod-backend
```

### Политика авторизации

- Сохраняем вход ADMIN через `/hub-api/admin/login` и проверку `/api/auth/me` на каждом запросе.
- Роли и права конкретных операций берём из оригинального backend; не предполагаем, что все операции доступны `CASHIER`.
- Отдельное решение о доступе кассиров к `admmm.sizey.ru`: текущий `actor()` запрещает не-ADMIN. Не ослаблять его глобально. Если понадобится, ввести явно ограниченные маршруты и разделы, серверные permission checks и тесты на запрет.
- Для мутаций: same-origin, CSRF/Origin, строгая схема входа, размер и частота запросов, таймаут, запрет автоматического повтора неидемпотентных запросов; журнал действий исходного backend.
- Не логировать access token, пароли, персональные данные и тела запросов с секретами. Выдача временных паролей — только по существующему проверенному сценарию.

## Этапы

### 0. Получить контракт действующего backend (блокирует реализацию записи)
- Найти исходники `app.sizey.ru` и `sizey-prod-backend` либо получить документированный OpenAPI/список роутов и DTO.
- Для каждого действия собрать: метод, путь, запрос/ответ, роль, бизнес-валидацию, аудит, идемпотентность, пагинацию, коды ошибок.
- Проверить функциональные экраны: клиенты (создание/редактирование/поиск), уровни, начисление, списание, продажи, возвраты, история, сотрудники, отчёты, настройки, клиентские пароли.
- Установить безопасную серверную сетевую связность `sizey-hub-api` -> `sizey-prod-backend`, без открытия внутренних портов наружу.

### 1. Read-only API и интерфейс
- Выделить `server/loyalty-admin-client.mjs`: allowlist конкретных upstream endpoints, серверная авторизация, валидация DTO и timeout.
- Добавить namespace `/hub-api/admin/loyalty/*` с проверкой ADMIN, отдельно от `/hub-api/loyalty` для покупателей.
- В `src/admin/` добавить раздел «Бонусная система» с поиском клиентов, карточкой, балансом, историей и уровнями. Не удалять ссылку на старый кабинет.
- Тестировать 401/403, устаревшую сессию, таймаут, недоступный backend и отсутствие утечки токенов.

### 2. Операции записи (только после проверки контрактов)
- Начисления, списания, продажи, возвраты, изменение клиентов, настройки и сотрудники — по одной группе за раз.
- Для каждой операции: серверная проверка роли, подтверждение в UI, защита от дублей и повторных отправок, точное отображение ответа backend, обновление баланса после успеха.
- Не подменять backend расчёт бонусов локальными вычислениями.

### 3. Параллельная эксплуатация и выпуск
- Контрактные и интеграционные тесты с фиктивными данными; ни один тест не меняет боевые балансы.
- Проверить, что действия в `app.sizey.ru` отображаются в `admmm.sizey.ru` и наоборот; сравнить права ADMIN/CASHIER и аудит.
- Включать новые разделы поэтапно с возможностью скрыть их без отката бонусной системы.
- Перед публикацией — резервные копии, canary, health checks и проверка текущего кабинета. Откат ограничен Hub Admin/BFF.

## Критерии готовности

- Старый кабинет работает без изменений.
- Оба интерфейса показывают одинаковые данные и используют единые backend-операции.
- Нет повторных начислений при повторе запроса, двойном клике или сетевом сбое.
- Сотрудник не получает операций выше своей роли.
- В браузер не попадают серверные токены и секреты.
- Сохраняется исходный журнал бонусных операций.
- Деплой и откат новой админки не затрагивают работающий бонусный кабинет.

## Следующее внешнее требование

Нужны исходники действующего `sizey-prod-backend` и Next.js кабинета либо документированный контракт API. Без них нельзя безопасно реализовать полный функционал записи.
